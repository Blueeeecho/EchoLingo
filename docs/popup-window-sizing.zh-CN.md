# 翻译浮窗尺寸约定

- 新的一次翻译／输入展示先按内容自动适配高度；宽度继续使用已有用户宽度偏好。
- 用户在当前展示中通过系统原生边缘调整了**高度**后，该展示优先保持用户高度。内容变化使用内部滚动，不反复把窗口拉回自动高度。
- 只拖宽度、只移动窗口、切换固定按钮、程序布局或 DPI 变化，不作为新的手动高度设置。
- 手动高度按展示 epoch 隔离，不写入永久设置。新一轮展示恢复自动高度，即使文字和测得内容高度与上一轮相同。
- 缩到最小高度时，原文、译文及译文操作区均能通过内容区滚动访问。工具栏仍在内容滚动区外。
- Windows 使用原生进入／退出尺寸调整通知；macOS 使用 NSWindow 的开始／结束 live resize 通知。普通 resize 事件只通知布局，不证明用户在拖边缘。

## 验证范围

Rust 状态测试检查手动高度优先级、仅改宽度、新旧 epoch 与无效高度；macOS 隐藏窗口测试检查通知安装和程序调整不会伪装成 live resize；浏览器测试通过真实前端和 mock IPC 检查布局、固定按钮、新展示重新测量及小视口滚动。

这些测试不代替实机连续拖边、混合 DPI、真实 WebKit 首帧清晰度验收。原生尺寸已应用的 ACK 也不等于页面已完成合成绘制。

## 原生边缘实机验收（macOS / Windows）

1. 打开译文浮窗，分别把鼠标移到左、右、上、下的**实际可见边缘**及四角；记录能否直接进入尺寸调整，不要求往正文里移动。不要把外围阴影当成已保证的 8px 热区。
2. 每条边连续拖大、拖小再松开；窗口应跟手，松开后不跳回自动高度。缩小时滚动仍能到达完整译文和底部操作。
3. 点固定／取消固定，位置和用户高度应不变；拖工具栏只移动窗口，点按钮不应触发原生标题栏拖动。
4. 从浮窗进入设置再返回，检查顶部没有多出系统标题栏／按钮或 32px 位移；点击输入框输入文字，快捷键及原文编辑仍正常。
5. 双屏或不同缩放下重复边缘拖动；再发起新翻译，确认新展示恢复内容适配。连续打开数次观察首帧是否仍先糊后清晰。

CI 中投递给自有窗口的 AppKit 事件只验证窗口内部事件路由、布局与输入；即使原生框架改变了尺寸，也不能证明 WindowServer 会把窗口外侧的物理点击交给它。实际外围可操作范围以上述实机步骤为准，不通过全局鼠标钩子截获其他窗口输入。

## Windows 可见边线只读命中记录（2026-10-30）

候选 `c9e1246a0e4505cfb3b3aa28d412498b30a3a85b` 的 [CI Windows 作业](https://github.com/Blueeeecho/EchoLingo/actions/runs/41045957365/job/124029984761) 已执行实际应用测试：浮窗和设置各 48 个采样点，八个边／角、可见线外 1／2 物理像素、线上及向内采样。两组观测前后窗口、DWM 可见边界、客户区与 DPI 均保持一致，既有真实拖动和尺寸保持验收也通过。

实际 runner 为 **96 DPI**；`SM_CXFRAME / SM_CYFRAME / SM_CXPADDEDBORDER` 均为 4 物理像素。以 DWM 可见矩形为参考，右／下边的线上点指矩形内最后一个像素（RECT 的 right／bottom 不包含在矩形内）：

| 区域 | 原生只读命中结果 |
| --- | --- |
| 左／右／下边线上、外侧 1 和 2 px | `HTLEFT / HTRIGHT / HTBOTTOM`；`WindowFromPoint` 亦属于自有主窗 |
| 左下／右下角外侧 1 和 2 px | `HTBOTTOMLEFT / HTBOTTOMRIGHT`；亦属于自有主窗 |
| 顶边及顶角线上 | 返回对应顶部缩放命中码；亦属于自有主窗 |
| 顶边／顶角上方 1 和 2 px | `HTNOWHERE`，不属于自有主窗；不宣称上方额外外扩热区 |

这说明该环境已存在贴边及部分外沿的原生尺寸调整区域；不需要额外扩展窗口外输入捕获。现有向内 10 CSS px 的 DOM 边缘仍作为兼容入口保留，没有据此扩大或移除已有手势区域。

**证据边界：**`WM_NCHITTEST` 仅直接发送给测试应用自有主窗，不投递外部窗口；`WindowFromPoint` 只记录所有权。强制向主窗查询某个外侧坐标的返回值，并不等于该坐标的真实鼠标按下／拖动已获操作系统投递。客户区中所有权布尔值为 false 也可能来自跨进程 WebView，不能据此认定其他应用遮挡。负坐标和 192 DPI 换算有纯函数自测，但本轮没有真实 HiDPI／跨屏拖动验收；最终仍按上面的实机步骤确认。
